# 做 D365 变更

## 读与写是两套工具

| 你想做的事 | 用这个 | 不写入 |
| --- | --- | --- |
| 看这个环境有什么 | `d365_envs`、`d365_metadata`、`d365_layers`、`d365_refs` | 只读 |
| 比两个环境差在哪 | `d365_snapshot` → `d365_diff` | 只读 |
| 插件注册 / 选项值契约漂移 | `d365_contract` | 只读 |
| 只看业务记录 | `d365_data` | 只读 |
| 改字段、显示名、选项值、视图列、移除自定义层 | `d365_metadata_write`（`plan-*` → `execute`） | `plan-*` 不写 |
| 改安全角色：谁有、能做什么、加/减权限 | `d365_roles`（`plan-*` → `execute`） | `plan-*` 不写 |
| 改一条记录 | `d365_data_write` | 会弹确认卡片 |
| 批量搬 / 批量改记录 | `d365_data_sync`（`plan` / `plan-update` → `execute`） | `plan*` 不写 |
| 导入某个解决方案会不会覆盖别人 | `d365_migrate` | 只读评估 |
| 这条 MR 的改动在目标环境跑不跑得起来 | `d365_code_check` | 只读 |

## 计划 → 确认 → 执行

所有元数据写入、角色变更、批量记录变更都走同一套契约：

1. `plan-*` 返回一个计划 id，**什么都没写**。计划内容是完整的操作清单（目标、旧值、新值）。
2. 人确认的是计划 id 与清单，不是一句"可以"。确认卡片在对话里，`execute` 才真正写入。
3. 计划是**一次性的**：执行时会先上锁、再从磁盘重新读一遍。确认之后被取消、被别的窗口执行过、或环境 URL 改过的计划都会被拒绝——不要自己编造 id，也不要复用上次的 id。
4. 执行完读凭据记录里的 `applied` / `failed`。**失败不回滚**：已经写成功的那部分留在环境里，失败的项要单独修。

## 权限

| 能力 | 覆盖什么 | 默认 |
| --- | --- | --- |
| `metadata.read` | 读元数据、层、表单、视图 | 开 |
| `data.read` | 读业务数据：记录、跟踪日志、作业、性能 | 关 |
| `data.write` | 改业务记录 | 关 |
| `message.invoke` | 调 POST 动作；**同时还要 `data.write`** | 关 |
| `role.admin` | 安全角色与权限 | 关 |
| `optionValue.add` 等 | 对应的元数据写入动作，逐个授予 | 关 |

权限在设置页「D365 工具箱 → 权限」里按环境授予。被拒时错误里会写缺哪个能力，照着改，不要换一条路绕过。

## 变更纪律

- **先只读**：`d365_metadata` / `d365_layers` / `d365_refs` 先看清要改的东西，再出计划。层叠（`d365_layers`）里最上面一层不是你的未受管层时，改了也会被盖住。
- **先在 DEV 出计划**：读一遍计划的 summary，确认命中条数、目标表、旧值。计划生成后环境变了，执行会拒绝——重新出计划，不要重试同一个 id。
- **不可恢复的动作**：删字段、删选项值、`RemoveActiveCustomizations`（移除整层自定义，含别人加在同一层的改动）需要显式 `acknowledge: true`。删字段和删选项值没有回收站。
- **选项值删除**：先确认没有记录还用着这个值；标签修改是安全的，值删除不是。
- **`d365_data_sync` 的 id**：GUID 或备用键 `字段='值'`（例如 `contoso_code='001'`），裸字符串会被拒。
- **搬运的 lookups**：同批里被引用记录还没建好的，会延后到第二轮回填；回填不上的记录会记为失败并写明原因。
- **发布在后台**：元数据写入的发布是异步的，`execute` 返回不代表已发布完；`d365_diagnose action=health` 看该环境是否还在发布。

## "没有阻断项"不等于"可以发布"

`d365_migrate` 和 `d365_code_check` 都会把**没法核对**的项单独列出来（层类型未映射、缺名称、探测失败、MR 里拿不到 diff、表/表单读取被截断）。结论只有在"零严重项且零未核对项"时才是"可以发布"。看到 `未能核对` / `未确认` 就当作"我还没查"，不要当作"没问题"——这两类输出是给人看的待办，不是绿灯。

`d365_diff` 同理：一侧快照不完整时，缺失的行标 `未确认`，不标 `已删除`。

## 不要做的事

- 不要在生产环境直接 `execute`；先在 DEV / SIT 跑通同一份计划。
- 不要自己拼计划 id、改计划文件、或绕过确认卡片直接调接口。
- 不要把 `clientSecret` 写进文档、提交或对话；设置页保存的密钥在 `d365.secrets.json`（明文，已在 `.gitignore`）。
- 不要用 `d365_data_write` 逐条改几十条记录：用 `d365_data_sync plan-update`，一次计划一次确认。
